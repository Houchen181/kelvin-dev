# Kelvin roadmap: every VISION.md requirement, and where it stands

Updated as work lands. "Done" means built, tested and on `main`; "partial" says what is missing.

| # | VISION requirement | Status | What exists / what is next |
|---|---|---|---|
| 1 | Integrated instruments, faster than a generic harness | done | Cards, safety gate, plans run in the engine (not one LLM turn per point), virtual lab; VISA/serial adapters (GPIB, USB, LAN, RS-232), read-only discovery (`kelvin-scan`, `scan_instruments`), 37 cards for common source-meters, lock-ins, temperature controllers, magnet supplies, lasers, preamps, meters, generators and AMO instruments. setup in the portal (scan, add by address, review limits, save and connect, switch back to the virtual lab); the desktop app opens on the user's `lab.yaml`; drivers for instruments behind vendor software (Zurich Instruments through LabOne, with discovery; Quantum Design through MultiPyVu) using the same command templates, so the gate and twins apply unchanged; card variables for per-installation names (Oxford Mercury iTC sensor UIDs, lock-in demodulators); instruments that answer every set (set_reply). Not yet verified on hardware: these follow the vendors' documentation |
| 2 | Keep projects confidential | done | Local-first app, data in `~/Kelvin`, nothing phones home, local OpenAI-compatible models, incognito chats (never saved, no memory); per-project rules on which model providers may see it and whether literature search may be used, enforced for chats, comparisons, both reviewers and tools, and stamped on each chat so moving it or deleting the project never loosens them; phone access only by paired devices |
| 3 | Caution; simulated experiment for trust | done | Measure/drive gate, limits, interlocks, guard readings, ramps, dry runs on twins when asked (and in auto mode), not as a routine step, one approval per plan, auto mode for low-risk runs, Stop |
| 4 | Customized instruments | done | YAML cards (connection settings, reply parsing, listen-only devices), lab config with per-instrument overrides, instruments added and edited from the portal, raw commands checked against cards; cards drafted from a manual (portal Cards dialog or `card_guide`/`check_card`/`save_card` in chat), checked and repaired, kept in `~/Kelvin/cards`; drafts are simulation-only for drives until a person marks them reviewed |
| 5 | Literature research to propose an experiment plan | done | `search_papers` (arXiv + OpenAlex, merged, with citations and abstracts) and `read_paper` (full text from arXiv HTML, equations as LaTeX, in parts); instructions to search before proposing parameters and to cite [Author Year](url), never inventing references; the plan is then dry-run as usual. Queries are kept free of confidential details; literature search can be switched off |
| 6 | Understand and test each instrument before use | done | Cards describe every parameter (measure/drive, units, limits, safe value); `describe_instrument`; health check on connect and before every plan: identity matches the card (catches a swapped address), error queue, every reading answers, card sanity checks, drives inside limits |
| 7 | Track all intermediate data and conditions | done | Event log, run folders (plan, data, snapshots before/after, analysis), live view |
| 8 | Experiment summary/log as PDF or PPT | done | Automatic and structured (project → device → scan): each scan's report in its run folder, each device's report and each project's master report in reports/<project>/, with index.csv and a dated history (Settings → Reports; on by default). `make_report` in chats and **Report…** in the Runs pane: a run, a chat's or project's runs, a day or the last N, as PDF and/or editable 16:9 slides. Summary in the user's or Kelvin's words; plots with fits, results with uncertainties, assessment, conditions, plan, approvals and alarms, lab log, project notes. Written without extra software; open or download from the portal |
| 9 | Concise, accurate responses | done | Short tool answers, assessments with uncertainties, prompt rules, plots instead of numbers |
| 10 | Mobile access, remote control | done | Phone access (off by default): a separate network listener where only paired devices work, never the desktop key; pairing by a one-time 6-digit code or QR code (lockout after wrong codes); roles watch (see, stop, decline) and control (also chat and approve); settings, instruments and lab config stay desktop-only; phone page with alarms, approvals, run progress and Stop; Tailscale addresses for access away from the lab; push via the ntfy webhook |
| 11 | Better literature review | done | Papers read in full where available; per-project reading list (`save_paper`, Project settings) that Kelvin sees in the project's chats and reports list as references; second opinions can check a review's conclusions |
| 12 | Virtual reviewer | done | A reviewer model (Settings) reads every plan before it runs: request, lab state, Kelvin's checks, plan; verdict go/caution/stop with reasons, shown in the chat and logged; "stop" asks the user before running. **Second opinion** on any answer (agree/partly/disagree), which the main model sees with the next message. The reviewer has no tools |
| 13 | Monitor sensitive instruments, report errors in time | done | Background watches with a range and a hold time (lab time); alarms when an instrument stops answering or reports an error; watches written in the lab config can stop the run and send named drives to safe (only to safe); people add watches in the Lab panel and Kelvin with `watch`/`watches`/`unwatch`; alarm banner, event log; guard readings during ramps and health checks before runs |
| 14 | Memory: keep important steps, not random questions; global/project/conversation scopes that do not leak | done | Global instructions and learned preferences; project instructions and typed notes; `remember` tool with scope and kind, de-duplication, corrections (`replaces`); notes recalled per message, by relevance in big projects, never into the system prompt; "Recalled N notes" in each reply; learning switch; incognito chats |
| 15 | Notifications | done | In-app notices and alarm banner; system notifications for alarms, and for approvals and finished runs while Kelvin is in the background; optional webhook (ntfy for phones, Slack, Teams, Discord) for the kinds the user ticks, URL kept as a secret; browser notifications on the approval page |
| 16 | Parallel conversation with several models | done | Claude, GPT, Gemini and local models per chat; **Compare** sends a message to two or three models at once, answers stream side by side (reading the lab only), and the user continues with the answer they choose |

Also asked for (2026-10-17): native detection and control of the usual instruments once the app is installed (cryostats and temperature controllers, lasers, lock-ins, current/voltage sources, amplifiers, ...). Status: adapters, discovery, cards and portal setup done.

Also asked for (2026-10-18): on installation, detect the connected instruments and set up communication with them; for each, find its accurate manual and its settings under its own working folder, and keep them for later complex scans. Status: done. On start, until the user has a lab, Kelvin scans, writes a lab config locked to observing (`observe_only`: reading and configuring work, drives stay at safe until a person reviews the limits and unlocks), and connects it. Each instrument gets `~/Kelvin/instruments/<name>/` with its parsed identity, the connection framing that answered, all settings read at setup (refreshed each start) and the maker's manual (17 of 21 cards link a verified manual on the maker's own site; the others take a PDF the person chooses). The agent reads them through `instrument_info` and `search_manual` (passages with page numbers) before involved scans. Checked on real manuals (SR830, Thorlabs ITC4000 reference); not yet run against real connected hardware.

Also asked for (2026-10-18): set the path for the data, and a terminal-like window similar to Claude Code (chosen: a terminal pane in the app). Status: done. Settings → Data folder moves runs, the lab record and reports to any folder (optionally with what is saved; nothing overwritten; falls back with a notice if unwritable at start). The terminal pane talks to Kelvin in text or sends an instrument its own commands through the same gate, with approvals answered inline (y/N) and every command logged as the person's.

Also asked for (2026-10-18): say why Kelvin is on the virtual lab, log what the start-up scan found, and find network and USB instruments without extra drivers. Status: done. A survey (survey.py) records what each scan looked through: the VISA in use, the local network (VXI-11 broadcast, mDNS adverts for VXI-11, HiSLIP and raw SCPI), USB through a bundled libusb (instruments recognised by USBTMC interface or maker ID, with the missing driver named), serial ports and GPIB adapters. The Lab panel and the chip in the sidebar give the reason in a sentence with the details, Set up's Scan shows the same, and each start-up scan goes to kelvin.log. Network search can be switched off in Settings. Not yet run against real network or USB instruments.

Also asked for (2026-10-18): uninstalling removes all of Kelvin's own data but not the experimental data. Status: done (Kelvin.exe --remove-data, run by the Windows uninstaller; checked in the release build).

Also asked for (2026-10-18): for an instrument it doesn't know, search for its manual, write its card, and set it up. Status: done (autocard.py). The model suggests the maker's addresses (plus known patterns), pages are followed one step to their PDFs, a manual counts only if downloaded and naming the model, the card is drafted from its command pages and checked, and whatever the model wrote it is made safe: draft (outputs simulation-only, settings ask), no on_connect, no reads that start something, calibration/firmware blocked, identity pattern from the real reply. At start-up the instrument joins the watching-only lab with its manual in its folder; Set up has a button for later scans. Not yet tried with a real unknown instrument and a real model.

Also asked for (2026-10-18): support the common AMO instruments (AOM, EOM, AWG...) and configure pulsed ODMR on NV centers. Status: done. pulses.py builds and checks the sequences (cw, pulsed_odmr, rabi, ramsey, hahn_echo, t1: laser, microwave and gate channels with per-channel delays; resolution, overlap and microwave duty-cycle checks); `show_sequence` draws one before it runs, and starting one is a drive. The virtual lab has an NV center (sim/nv.py) with a pulse generator, a microwave source and a photon counter; analysis fits Rabi oscillations and reports the pi time. Drivers for the Swabian Pulse Streamer, SpinCore PulseBlaster and Swabian Time Tagger; cards for SRS SG384, R&S SMB100A, Keysight N5183B, Windfreak SynthHD (draft), SRS DG645, Rigol DG1000Z, MOGLabs XRF and Novatech 409B, with value-first commands (ON,1) and settings that have no read-back. Tested against fakes of the vendor libraries and instruments; not yet run on real hardware.

Also asked for (2026-10-18): talk to instruments with a web or network API, such as M Squared lasers, PHAROS lasers and RFSoC boards. Status: done. http(s):// web APIs (webapi.py: JSON bodies, field selection, bearer token from an environment variable), m2:// for M Squared ICE-BLOC controllers (JSON over TCP with the start_link handshake and task reports), toptica:// for the DLC pro command line, qick:// for RFSoC boards through QICK's Pyro4 server (tone or pulses with I/Q readout; generators reset to zero when the output goes off or on disconnect). Cards for the SolsTiS, PHAROS (output and attenuator only; start, presets and interlock resets stay with people), DLC pro (draft until the current's unit is checked) and QICK. Written from the makers' protocol documents and libraries, tested against fakes; not yet run on real hardware.

Also asked for (2026-10-18): develop new instrument cards, including from the maker's control-script examples (e.g. the attoDRY cryostat). Status: done. Cards can drive an instrument through the maker's Python module or DLL (library section: module, or dll with each function's C signature from the header; open/close calls; toggle switches read before toggling) at lib:// addresses that name the Python to use (32-bit for a 32-bit DLL) and the maker's folder. The library runs in a helper process (data/bridge/kelvin_bridge.py; Kelvin.exe --bridge in the app) that loads only the named module or DLL from that folder or an installed package, never the standard library or a system DLL, and calls only the card's functions; readings must call read-only functions. Drafting takes example scripts as well as manuals (several files in the portal; read_examples in chat), and try_card / Try it asks the instrument who it is and reads every reading without setting anything (queries only for text instruments), so a card is fixed until its readings match the front panel. An attoDRY1100/2100/800 card (draft) from attocube's header. Tested with a fake maker's module and a C library standing in for a DLL; not yet run with a real attoDRY.

Also asked for (2026-10-18): a queue to line up scans, modelled on Special Measure's queue (smaux.smq: enqueue at a position, u/d to reorder, delete, text items between scans, run in order). Status: done. scanqueue.py: items are plans or steps (set values, stabilize on a reading, wait), added at any position with a note, moved, edited, removed or put back in line while the queue runs; kept per lab in queue.json, never auto-started after a restart. Start checks every item, dry-runs the whole queue in order on one simulated copy of the lab, and asks a person once for every drive range (the gate's standing grants cover the queue's scans; anything outside asks again). It runs in the background; chat tools answer 'busy' instead of blocking; a failure, decline or Stop pauses it (or it goes on, by choice); Pause stops after the current item. Named queues are saved and loaded as YAML. Chat tools queue_show/add/edit/change/start/pause/save/load, the Queue view in the Runs pane, and 'Add to the queue' on a finished run. Also fixed: approvals not tied to a chat (a queue's, another agent's run) were drawn in the Lab panel and wiped on the next refresh.

Also asked for (2026-10-19): experimental data storage and PDF/PowerPoint reports should be automatic, by default. Status: done. Runs were already saved point by point; each finished run now also gets data.csv (and one CSV per trace reading) and its report, report.pdf and report.pptx, in its own folder, and a queue that ends or pauses gets one report of its runs in reports/. Settings → Reports: PDF and PowerPoint (default), one of them, or only when asked; CSV is always written. The Runs pane opens the report, slides, CSV and folder.

Also asked for (2026-10-19): log-in, with each user's own path and record, and no lab owner. Status: done. accounts.py keeps the accounts (name, optional password as a PBKDF2 hash); anyone can add one and all are equal. Signing in points settings, API keys (encrypted with the password when there is one), the ChatGPT sign-in, chats, projects, memory, the data folder, queue, mounted sample and record (events.jsonl) at that person's folder in ~/Kelvin/users/<name>; the instruments, cards, lab config and the lab's instrument log (instrument-log.jsonl, every event with the person's name) are shared. Changing person is refused while a plan or queue runs (anyone can stop it); open approvals are declined and auto mode is switched off. One account without a password signs in by itself; the first account takes over the data from before accounts. Phones are paired per person. Uninstalling removes every person's settings and chats and keeps their data.

Also asked for (2026-10-19), temporary: use the Claude Code signed in on this computer for chats, and have Claude operate the computer. Status: done, developer only (from source or a private build; never in a release, per Anthropic's terms), to be removed. Chats run `claude -p` with Kelvin's prompt and tools (calls come back to Kelvin's loop and gate); operate_computer gives Claude Code Kelvin's screen tools, records every step, and locks Kelvin's approvals and settings while it runs. See docs/development.md.

Also asked for (2026-10-21): one central account database for all Kelvin users, just accounts and passwords: a login for the Kelvin app that works on every computer, with no data sharing for now. Status: built, waiting on the hub going online for good (then `central.DEFAULT_HUB` gets its address). The hub signs people in with JSON (`/api/signin`, `/api/register`, `/api/reset`, `/api/password`). central.py is Kelvin's client. Once a computer knows the hub, its sign-in screen asks for email and password, and keeps a hash of the password for signing in offline. A person signing in on a computer for the first time can take over one of its accounts from before, which keeps its chats, data and keys. A password changed elsewhere asks once for the old one to keep the keys. Sharing work with the hub (hubsync.py) is switched off (`HUB_SHARING`).

Also asked for (2026-10-19): reports organized with a clear structure: per scan, per device (the sample under test) and a master report per project. Status: done. Devices are kept per project (Project settings → Devices) with a General workspace outside projects; the Lab panel's Sample says which is mounted, and every run records its project and device (a plan may name another device with device:). reports/document.py renders documents of fixed numbered sections to PDF and PowerPoint; reports/kinds.py builds the scan report (Result, Plots, Method, Conditions, Approvals and alarms, Appendix), the device report (The device, Mount history, Results by measurement, Trends, Ranges explored, Problems, Scan index) and the master report (Summary, Goals and decisions, Devices compared, Main results and figures, Timeline, Open questions and issues, References, Index) from run digests, without a model. reports/<project>/ holds the master, devices/, history/ (a dated copy per day) and index.csv; queues/ and custom/ hold the rest. Device and master reports are rewritten about 20 s after a scan (once for a burst), or at once with Update now. The master report opens with the person's words, or Kelvin's (Write the opening with Kelvin, if the project's rules allow the model). The Reports dialog is a library of all of them; make_report takes kind project, device or scan; the chat has devices, add_device and mount_device.
