# Kelvin roadmap: every VISION.md requirement, and where it stands

Updated as work lands. "Done" means built, tested and on `main`; "partial" says what is missing.

| # | VISION requirement | Status | What exists / what is next |
|---|---|---|---|
| 1 | Integrated instruments, faster than a generic harness | done | Cards, safety gate, plans run in the engine (not one LLM turn per point), virtual lab; VISA/serial adapters (GPIB, USB, LAN, RS-232), read-only discovery (`kelvin-scan`, `scan_instruments`), 18 cards for common source-meters, lock-ins, temperature controllers, magnet supplies, lasers, preamps, meters and generators. setup in the portal (scan, add by address, review limits, save and connect, switch back to the virtual lab); the desktop app opens on the user's `lab.yaml`; drivers for instruments behind vendor software (Zurich Instruments through LabOne, with discovery; Quantum Design through MultiPyVu) using the same command templates, so the gate and twins apply unchanged; card variables for per-installation names (Oxford Mercury iTC sensor UIDs, lock-in demodulators); instruments that answer every set (set_reply). Not yet verified on hardware: these follow the vendors' documentation |
| 2 | Keep projects confidential | done | Local-first app, data in `~/Kelvin`, nothing phones home, local OpenAI-compatible models, incognito chats (never saved, no memory); per-project rules on which model providers may see it and whether literature search may be used, enforced for chats, comparisons, both reviewers and tools, and stamped on each chat so moving it or deleting the project never loosens them; phone access only by paired devices |
| 3 | Caution; simulated experiment for trust | done | Measure/drive gate, limits, interlocks, guard readings, ramps, dry run of every plan on twins, one approval per plan, auto mode for low-risk runs, Stop |
| 4 | Customized instruments | done | YAML cards (connection settings, reply parsing, listen-only devices), lab config with per-instrument overrides, instruments added and edited from the portal, raw commands checked against cards; cards drafted from a manual (portal Cards dialog or `card_guide`/`check_card`/`save_card` in chat), checked and repaired, kept in `~/Kelvin/cards`; drafts are simulation-only for drives until a person marks them reviewed |
| 5 | Literature research to propose an experiment plan | done | `search_papers` (arXiv + OpenAlex, merged, with citations and abstracts) and `read_paper` (full text from arXiv HTML, equations as LaTeX, in parts); instructions to search before proposing parameters and to cite [Author Year](url), never inventing references; the plan is then dry-run as usual. Queries are kept free of confidential details; literature search can be switched off |
| 6 | Understand and test each instrument before use | done | Cards describe every parameter (measure/drive, units, limits, safe value); `describe_instrument`; health check on connect and before every plan: identity matches the card (catches a swapped address), error queue, every reading answers, card sanity checks, drives inside limits |
| 7 | Track all intermediate data and conditions | done | Event log, run folders (plan, data, snapshots before/after, analysis), live view |
| 8 | Experiment summary/log as PDF or PPT | done | `make_report` in chats and **Report…** in the Runs pane: a run, a chat's or project's runs, a day or the last N, as PDF and/or editable 16:9 slides. Summary in the user's or Kelvin's words; plots with fits, results with uncertainties, assessment, conditions, plan, approvals and alarms, lab log, project notes. Written without extra software; open or download from the portal |
| 9 | Concise, accurate responses | done | Short tool answers, assessments with uncertainties, prompt rules, plots instead of numbers |
| 10 | Mobile access, remote control | done | Phone access (off by default): a separate network listener where only paired devices work, never the desktop key; pairing by a one-time 6-digit code or QR code (lockout after wrong codes); roles watch (see, stop, decline) and control (also chat and approve); settings, instruments and lab config stay desktop-only; phone page with alarms, approvals, run progress and Stop; Tailscale addresses for access away from the lab; push via the ntfy webhook |
| 11 | Better literature review | done | Papers read in full where available; per-project reading list (`save_paper`, Project settings) that Kelvin sees in the project's chats and reports list as references; second opinions can check a review's conclusions |
| 12 | Virtual reviewer | done | A reviewer model (Settings) reads every plan before it runs: request, lab state, Kelvin's checks, plan; verdict go/caution/stop with reasons, shown in the chat and logged; "stop" asks the user before running. **Second opinion** on any answer (agree/partly/disagree), which the main model sees with the next message. The reviewer has no tools |
| 13 | Monitor sensitive instruments, report errors in time | done | Background watches with a range and a hold time (lab time); alarms when an instrument stops answering or reports an error; lab-owner watches in the lab config can stop the run and send named drives to safe (only to safe); people add watches in the Lab panel and Kelvin with `watch`/`watches`/`unwatch`; alarm banner, event log; guard readings during ramps and health checks before runs |
| 14 | Memory: keep important steps, not random questions; global/project/conversation scopes that do not leak | done | Global instructions and learned preferences; project instructions and typed notes; `remember` tool with scope and kind, de-duplication, corrections (`replaces`); notes recalled per message, by relevance in big projects, never into the system prompt; "Recalled N notes" in each reply; learning switch; incognito chats |
| 15 | Notifications | done | In-app notices and alarm banner; system notifications for alarms, and for approvals and finished runs while Kelvin is in the background; optional webhook (ntfy for phones, Slack, Teams, Discord) for the kinds the user ticks, URL kept as a secret; browser notifications on the approval page |
| 16 | Parallel conversation with several models | done | Claude, GPT, Gemini and local models per chat; **Compare** sends a message to two or three models at once, answers stream side by side (reading the lab only), and the user continues with the answer they choose |

Also asked for (2026-10-17): native detection and control of the usual instruments once the app is installed (cryostats and temperature controllers, lasers, lock-ins, current/voltage sources, amplifiers, ...). Status: adapters, discovery, cards and portal setup done.

Also asked for (2026-10-18): on installation, detect the connected instruments and set up communication with them; for each, find its accurate manual and its settings under its own working folder, and keep them for later complex scans. Status: done. On start, until the user has a lab, Kelvin scans, writes a lab config locked to observing (`observe_only`: reading and configuring work, drives stay at safe until a person reviews the limits and unlocks), and connects it. Each instrument gets `~/Kelvin/instruments/<name>/` with its parsed identity, the connection framing that answered, all settings read at setup (refreshed each start) and the maker's manual (17 of 21 cards link a verified manual on the maker's own site; the others take a PDF the person chooses). The agent reads them through `instrument_info` and `search_manual` (passages with page numbers) before involved scans. Checked on real manuals (SR830, Thorlabs ITC4000 reference); not yet run against real connected hardware.

Also asked for (2026-10-18): set the path for the data, and a terminal-like window similar to Claude Code (chosen: a terminal pane in the app). Status: done. Settings → Data folder moves runs, the lab record and reports to any folder (optionally with what is saved; nothing overwritten; falls back with a notice if unwritable at start). The terminal pane talks to Kelvin in text or sends an instrument its own commands through the same gate, with approvals answered inline (y/N) and every command logged as the person's.

Also asked for (2026-10-18): say why Kelvin is on the virtual lab, log what the start-up scan found, and find network and USB instruments without extra drivers. Status: done. A survey (survey.py) records what each scan looked through: the VISA in use, the local network (VXI-11 broadcast, mDNS adverts for VXI-11, HiSLIP and raw SCPI), USB through a bundled libusb (instruments recognised by USBTMC interface or maker ID, with the missing driver named), serial ports and GPIB adapters. The Lab panel and the chip in the sidebar give the reason in a sentence with the details, Set up's Scan shows the same, and each start-up scan goes to kelvin.log. Network search can be switched off in Settings. Not yet run against real network or USB instruments.
